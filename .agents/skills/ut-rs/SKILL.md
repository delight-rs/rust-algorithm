# 算法单元测试生成

## 何时使用

- 用户给出一个算法源文件（路径或代码），要求生成或补充单元测试。
- 用户说「生成 UT」「补几个测试用例」「用测试验证这个实现」。
- 不适用：要求修改或优化算法实现、只解释代码、生成 Markdown 分析笔记。

## 硬性约束

1. **上下文是前置门槛**：未拿到用户提供的题目上下文，不得直接写测试；也不得用文件里的链接、注释、题名或自己的推测替代用户输入。
2. **测试写在当前文件**：追加到被测源文件末尾的 `#[cfg(test)] mod test` 中；不新建 `tests/` 集成测试，不改 `mod.rs`。
3. **不改算法代码**：函数签名、实现、注释、格式保持原样。唯一允许的编辑是在文件尾部新增测试模块，或向已有测试模块追加用例。
4. **失败用例不得忽略**：禁止 `#[ignore]`、注释掉断言、删除用例、放宽断言或跳过不跑。失败要如实报告。
5. **不新增依赖**：默认只用 `std` 的 `#[test]`、`assert_eq!`、`assert!`；需要 `proptest`、`rstest` 等先征得用户同意。

## 工作流程

### 1. 索取题目上下文（必须，不能跳过）

开始前向用户提问，一次问清：

- 题面：输入、输出和返回值语义；
- 约束：数据范围、长度上下限、是否允许空输入，是否允许重复值、负数、零；
- 示例：至少一组题面示例及期望输出；
- 题源链接（可选，仅作补充，不能替代用户的文字说明）。

提问后**停下来等待用户回复**。若用户回复「没有题面，按代码推断」，先列出推断出的输入输出与边界，请用户确认后再继续。

### 2. 读取源码

- 完整读取目标文件，包括已有测试和题源链接注释。
- 记录所有公开函数（含 `_2`、`_3` 等变体）、参数与返回类型、是否有 `&mut` 参数、是否依赖外部状态。
- 若已有 `#[cfg(test)] mod test`，在现有模块内追加；没有才新建，模块名沿用仓库的 `test`。

### 3. 设计用例

- 文件中每个公开实现都至少覆盖一组题面示例，不要只测主函数。
- 边界维度按题目类型选择：空输入、单元素、全部相同、重复值、零、负数、最大/最小长度、结果溢出。
- 字符串题区分 ASCII 与多字节 UTF-8；涉及 `len`、`chars`、`as_bytes` 的实现在中文输入下要单独验证。
- 期望值必须独立手算或依据题面写出，不得调用被测函数自身生成期望。
- 一个用例验证一个行为，命名 `test_<函数名>_<场景>`；同一场景的多个变体加后缀区分。
- 不写依赖执行顺序或共享可变状态的测试。
- 不重命名已有的正确测试，不改动已有断言（除非用户要求）。

### 4. 写入测试

沿用仓库现有写法：

```rust
#[cfg(test)]
mod test {
    use super::Solution;

    #[test]
    fn test_product_except_self_example1() {
        let nums = [1, 2, 3, 4].to_vec();
        assert_eq!(Solution::product_except_self(nums), vec![24, 12, 8, 6]);
    }
}
```

- 只有自由函数时用 `use super::*;`，有 `Solution` 时用 `use super::Solution;`。
- 参数用 `vec![...]` 或 `[...].to_vec()`，与文件已有测试保持一致。
- 数组、切片、`Option`、`Result` 的期望值按实际返回类型书写，不用 `unwrap` 掩盖差异。
- 测试无需注释说明「这是什么」；用例名和输入数据要能自解释。

### 5. 运行测试

在仓库根目录执行，过滤词用函数名或模块名：

```sh
cargo test product_except_self
```

- 只运行与目标文件相关的测试，避免无关失败干扰判断。
- 条件允许时再跑一次 `cargo test` 确认没有影响其他模块。
- `cargo test` 可能输出无关警告，汇报时只保留与本次任务相关的信息。

### 6. 处理失败

1. **期望写错**：重新手算或对照题面，修正测试，并在汇报中说明改了什么。
2. **实现与期望不符**：保留失败用例，**不修改算法代码**；报告函数名、输入、期望值、实际值，并询问用户如何处理。
3. **编译错误**：只修测试代码；不得为通过编译改动算法签名或实现。
4. 任何情况下都不要用 `#[ignore]`、`#[should_panic]`（题目本身要求 panic 除外）或注释断言来「消灭」失败。

## 完成前检查

- [ ] 已收到用户提供的题目上下文，或用户确认过推断出的约束。
- [ ] 测试位于被测源文件内的 `#[cfg(test)] mod test`。
- [ ] 除新增测试外，算法代码零改动；可用 `git diff` 核对。
- [ ] 覆盖了文件中所有公开实现、题面示例和主要边界。
- [ ] 没有 `#[ignore]`、没有注释掉的断言、没有删除或放宽失败用例。
- [ ] 已实际运行 `cargo test <过滤词>`，并如实记录结果。
- [ ] 没有新增依赖。

## 汇报格式

完成后简要说明：

- 测试所在文件路径与新增用例数量；
- 覆盖了哪些函数、哪些边界场景；
- 实际运行的命令与结果（通过/失败数量）；
- 失败用例的输入、期望、实际值，以及判断（测试写错、实现有误或待确认）；
- 用户确认过的假设；未运行校验时说明原因。
