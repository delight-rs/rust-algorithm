# Rust 标准库方法文档整理

## 何时使用

用户提供一个或多个 Rust 文件（路径或代码），要求把它们用到的方法整理成文档、补充标准库 API 笔记，或更新 `docs/rust-standard-lib-methods.md` 时，使用本 skill。

如果用户只是问某个 API 怎么用，直接回答即可，不必走完整流程。

## 目标文件

- 只更新 `docs/rust-standard-lib-methods.md`。
- 原始说明里的 `rust-standard-lib-methods.md.rs` 是笔误，不要创建 `.md.rs` 文件。
- 动手前先完整读一遍现有文档，沿用其章节编号、表格写法和示例风格。
- 增量补充：不删除、但可重写已有内容

## 工作流程

1. **读源码**：逐个读取用户提供的 Rust 文件，按出现顺序记录所有标准库调用。
2. **列清单**：整理成「类型/模块 → 方法 → 出现位置」的清单并去重。
3. **补相关方法**：为每个方法补充 1–2 个直接相关项，范围见下文。
4. **查现有文档**：搜索方法名和章节标题；已讲过的只做补充或修正，不重复建条。
5. **归类**：按类型/主题放入合适章节；没有合适章节就新建，并保持编号连续。
6. **写作**：每个方法给出作用、复杂度、最小可运行示例和易错点。
7. **校验**：检查复杂度覆盖、示例可编译性和内容通用性。
8. **汇报**：列出新增/修改的章节和方法。

## 提取范围

必须覆盖源码中出现的：

- 固有方法与关联函数：`s.push_str(...)`、`Vec::with_capacity(...)`
- trait 方法：`Iterator`、`FromIterator`、`TryFrom`、`AsRef`、`Ord` 等
- 运算符背后的 trait：`Index`、`Add`、`PartialOrd`、`Deref` 等
- 自由函数与宏：`std::mem::swap`、`format!`、`vec!`
- 标准库类型上的常见组合：`Option`/`Result` 的 `map`/`and_then`/`?`，迭代器的 `map`/`filter`/`fold`/`collect`

忽略项目自定义函数和第三方 crate API；若为对照必须提及，明确标注「非标准库」。

## 相关方法怎么补

以「同一类型或同一模块 + 常见搭配」为边界：

- 源码用了 `String::push_str`，可补 `push`、`insert_str`，不必扩展到整个 `str` API。
- 源码用了 `iter().filter_map`，可补 `filter`、`map`、`flat_map`。
- 源码用了 `Vec::sort`，可补 `sort_by`、`sort_unstable`、`binary_search`。
- 源码用了 `HashMap::entry`，可补 `or_insert`、`or_insert_with`、`and_modify`。

每个方法最多补 1–2 个直接相关项；不要按字母表或整个模块无差别罗列。

## 章节组织

按类型/主题分类，不按源文件、不按题目。可延续现有文档的顺序：

1. `String` 与 `&str`
2. 字符与字节遍历
3. 迭代器与适配器
4. `Option` 与 `Result`
5. `Vec` 与 slice
6. 排序、查找与比较
7. `HashMap` / `HashSet`、`BTreeMap` / `BTreeSet`
8. 数值、位运算与 `char`
9. `mem`、所有权与类型转换
10. 复杂度速查
11. 易混点与陷阱
12. 测试常用写法

只保留本次涉及的主题；新增章节插到语义相近的位置，后续编号顺延。标题用 `## N. 主题`，子节用 `### N.M 子主题`，与现有文档保持一致。

## 单个方法的写法

优先用表格承载签名、作用、复杂度，再按需给最小示例：

| API            | 作用               | 时间                 | 空间 |
| -------------- | ------------------ | -------------------- | ---- |
| `s.len()`      | 返回字节长度       | O(1)                 | O(1) |
| `v.push(x)`    | 尾部追加元素       | 摊销 O(1)，最坏 O(n) | O(1) |
| `it.filter(p)` | 保留满足条件的元素 | 构造 O(1)，消费 O(n) | O(1) |

写作要求：

- 签名写标准库真实形态；泛型参数可省略，但接收者类型要清楚。
- 作用用一句话说清「做什么、返回什么」，不写实现细节。
- 每个方法都必须有时间、空间复杂度，不能留空或写「较快」。
- 时间按调用本身计算；迭代器适配器同时注明「构造 O(1)，消费 O(n)」。
- 空间指额外辅助空间；返回新集合时，把返回值占用计入并注明。
- 注明摊销、最坏情况和短路行为，例如 `Vec::push` 摊销 O(1)、最坏 O(n)；`any`/`find` 命中即停。
- 示例 3–8 行，使用中性变量名，能直接放进 `#[test]` 或 `fn main()` 编译。
- 易错点只写真正容易踩的：UTF-8 边界、下标按字节、`clone` 与 `Copy`、迭代器惰性、借用冲突等。

## 复杂度约定

统一用以下记号，并在相关章节开头说明一次：

- `n`：接收者的元素个数，字符串场景为字节数；`m`：参数长度或第二个集合的大小。
- 大小关系：O(1) < O(log n) < O(n) < O(n log n) < O(n²)。
- 「摊销」用于均摊后为常数的操作，同时给出最坏情况。
- 哈希表写「平均 O(1)，最坏 O(n)」，不要只写 O(1)。
- 稳定排序注意额外空间；不确定时查标准库文档或实现说明，不凭印象写。

## 通用性要求

文档必须独立于触发它的源文件：

- 不出现源文件的函数名、变量名、题目背景或输入输出约定。
- 示例用 `s`、`v`、`it`、`map` 等中性命名。
- 不写「本题中」「上面的代码里」「该算法需要」之类的句子。
- 示例覆盖典型用法即可，不要求复现源文件的业务逻辑。
- 结论要普适：说明方法适用于什么场景，而不是只解释某一次调用。

## 语言与排版

- 说明文字用简体中文，API、类型和代码保持英文。
- 方法名、类型名、字面量一律用行内代码。
- 表格用于并列比较，步骤和注意事项用短列表。
- 遵循仓库 `.markdownlint.json`：`MD013` 已关闭，长行不做强制换行。
- 不使用 HTML 标签；代码块标注 `rust`。

## 汇报格式

完成后用几句话说明：

- 更新了哪些章节，新增/修改了多少个方法；
- 哪些方法因已有内容而只做了补充；
- 校验方式和结果；
- 仍未覆盖的方法及原因（如果有）。
