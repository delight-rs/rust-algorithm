# 算法分析与笔记生成

## 何时使用

- 用户给出一个算法源文件或代码片段，要求分析其输入输出、解法、思路来源、复杂度或应用场景。
- 用户要求把某道算法题或某个算法实现整理成 Markdown 笔记。
- 用户要求解释「为什么想到这个方案」，或对比文件中的多种实现。

不适用：只问某个 API 的用法（直接回答）；只需要修 bug 或优化代码（直接改代码，除非用户同时要文档）。

## 输入与产物

| 项 | 说明 |
| -- | ---- |
| 输入 | 源文件路径；题源链接（若文件注释中有）；用户额外要求 |
| 产物 | 与源文件**同目录、同文件名**的 `.md` 文件，仅替换扩展名 |
| 示例 | `src/arrary/product_of_array_except_self.rs` → `src/arrary/product_of_array_except_self.md` |
| 位置约束 | **不要**默认放进 `docs/`；用户明确指定位置时才改变 |
| 源文件 | 默认只读，不修改；需要改代码时先确认 |

路径以工具返回的真实路径为准，不猜测、不纠正目录拼写（例如本仓库的 `src/arrary/` 保持原样）。

## 工作流程

1. **读全源码与测试**
   - 完整读取目标文件，包括 `#[cfg(test)]` 模块。
   - 记录函数签名、所有实现版本、测试用例与题源链接。
   - 有链接时核对题目的约束；没有链接时从类型、索引方式、测试数据反推，并在文档中标注为「代码隐含假设」。

2. **明确输入输出**
   - 用表格写清：参数名、类型、含义、取值范围、是否可空、是否可重复。
   - 用公式或伪代码定义输出，例如 `answer[i] = ∏ nums[j] (j ≠ i)`。
   - 列出边界：空输入、单元素、零、负数、重复值、极值、溢出、非法输入。
   - 区分「题目保证」与「代码自己处理」，不要混为一谈。

3. **拆解文件中的每个实现**
   - 全部覆盖，不只讲最优解；暴力解往往是思路推导的起点。
   - 每个实现写：核心思想、关键步骤、时间/空间复杂度、局限性。
   - 最优解要给出小规模运行状态追踪表，并说明循环不变量或正确性理由。
   - 指出易错点，例如更新顺序、下标边界、提前返回条件。

4. **还原「为什么想到这个方案」**
   - 从最直白的解法出发，指出瓶颈。
   - 描述尝试过的优化及**失败的本质原因**，不要只罗列边界情况。例如乘法场景不能「总量除自身」，根本原因是 0 没有逆元，而不只是「要特判 0」。
   - 写出换视角后的分解方式，例如把「排除 i」拆成「左段 × 右段」。
   - 说明为什么选择该数据结构/技巧，以及空间如何进一步压缩。
   - 抽象成可迁移的模板，并用对比表展示同类问题的共性。
   - 只写有依据的推导，不为了叙事完整而编造「曾经尝试过某某方案」。

5. **给出复杂度对比**
   - 表格列出：实现、时间、额外空间、前提/限制。
   - 明确「额外空间」是否包含输出；输出数组通常不计入额外空间，需注明。
   - 注明摊销、最坏情况、是否依赖逆运算、是否可并行。
   - 不臆造复杂度，一律以代码实际循环和分配为准。

6. **分析实际应用场景**
   - 用表格写：场景、被聚合的量、为什么用该方案而不是更简单的方案。
   - 只写可信的工程场景；生活化类比要明确标注为「类比」。
   - 说明工程约束：数值溢出、浮点精度、零值/无逆元、动态更新、流式处理、并行化。
   - 乘积类问题要指出大数场景常转对数域，以及何时仍必须用前后缀方案。

7. **补充延伸与测试评价**
   - 列出变体：换运算（和、最值、gcd、模乘）、加动态更新、升维。
   - 点评现有测试覆盖了哪些边界，还缺什么；可以建议补测，但不擅自修改测试。
   - 若发现实现与题面约束不一致，在文档中标注，不悄悄「修正」代码。

8. **写作与校验**
   - 按 `templates/analysis-template.md` 组织章节，可按算法特点增删，但保持「输入输出 → 解法 → 动机 → 复杂度 → 应用 → 延伸」的主线。
   - 写完后运行文末的校验命令，并在汇报中说明实际结果。

## 写作规则

- 说明文字用简体中文；函数名、类型名、变量名、路径用行内代码。
- 对比信息优先用表格；推导和步骤用短列表或编号列表。
- 展示数组状态变化时，用等宽 `text` 代码块或表格，保证列对齐。
- 需要图示时可用 `mermaid`，优先画高而不是画宽，不使用 HTML 标签和自定义样式。
- 遵循仓库 `.markdownlint.json`：本仓库已关闭 `MD013`，长行不强制换行。
- 每个结论都要有代码、约束或数学依据；不写「显然」「众所周知」之类空话。
- 引用源文件时使用项目相对路径；文档中的示例数据要与源码测试一致或明确标注为自造示例。
- 不使用「本题中」来替代通用解释；先讲清算法本身，再落到具体题目。

## 参考模板

章节骨架见 `templates/analysis-template.md`。模板只是结构提示，不必逐字填充；算法简单时可合并小节，但不要省略「输入输出」「思路来源」「应用场景」三部分。

## 校验

在仓库根目录依次执行（按实际情况替换文件名与测试过滤词）：

```sh
cargo test product_except_self
npx --yes markdownlint-cli src/arrary/product_of_array_except_self.md
```

- 只运行与目标文件相关的测试，避免无关失败干扰判断。
- 若测试未通过，先判断是代码问题还是测试问题；不要为了让测试变绿而篡改断言。
- 若命令无法运行，明确说明原因，不声称已通过。
- `cargo test` 可能输出无关警告，汇报时只保留与本次任务相关的信息。

## 完成前检查

- [ ] 输入、输出、约束、边界均已写清，且区分题面保证与代码假设。
- [ ] 文件中每个实现都被覆盖，最优解有状态追踪或正确性说明。
- [ ] 「为什么想到这个方案」包含朴素解法、失败原因、关键转折和可迁移模板。
- [ ] 复杂度与代码实际行为一致，已注明额外空间口径。
- [ ] 应用场景可信，工程限制（溢出、零值、精度、动态更新）有说明。
- [ ] 文档位于源文件同目录且同名，未误放到 `docs/`。
- [ ] 已运行相关测试与 markdownlint，并如实记录结果。
- [ ] 未修改源文件（除非用户明确要求）。

## 汇报格式

完成后简要说明：

- 生成的文档路径；
- 覆盖了哪些实现与分析维度；
- 实际运行的校验命令及结果；
- 文档中标注为假设、类比或存疑的内容。
